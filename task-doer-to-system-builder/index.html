The frame. Most ways of using Claude treat it as a code helper: faster XML, faster SOQL, faster Slack drafts. That works, but it caps out at "I type faster now." The shift over the last 3 months has been to treat Claude as the surface for a system I own: skills, rules, a knowledge graph, and memories that compound. Every notable session leaves an artifact behind, so the next session starts further along.

The numbers: 90 tickets and 148 points shipped solo across 5 sprints (Feb 23 to May 1). Volume is not the story. The story is what’s built underneath the volume.

The token economy

How the system pays back in real time

The compounding 6%. That share of every Claude session goes to building the system itself - new skills, rules, knowledge-graph entries. It's the only category of spend where more now means less later, because each new artifact discounts the cost of every future ticket that touches the same area. Everything else gets cheaper because of it.

Every Claude session needs context: how the org is set up, where things live, the team's conventions. The system in this doc means that context is loaded once and reused - skills, rules, and the knowledge graph stay in Claude's working memory across sessions. The less time Claude spends relearning, the more it spends shipping.

How the structure works

Each layer of context is loaded only when needed, not on every turn:

  • CLAUDE.md - a thin index of pointers, the only file loaded every session
  • 12 topic rule files in .claude/rules/ - field development, validation rules, permission sets, data imports, etc. Each loaded only when the work touches the topic
  • 80+ skills - loaded only when their trigger fires (a slash command, a keyword in the task)
  • lat.md knowledge graph - searched semantically; returns only the matching section, not the whole graph
  • Memory files - persisted across sessions, recalled when the topic comes up

That just-in-time shape is the efficiency mechanism. Nothing is preloaded; almost nothing gets re-read. A weekly auto-audit (/claude-efficiency-pulse, every Monday at 7am) scans the past 7 days of sessions for drift - long sessions, missed knowledge-graph briefings, repeated re-reads, rule-load patterns - and posts the findings to Slack. The discipline keeps the always-on budget lean: the most recent rule-cost grading cut about 14k tokens off every session's startup.

The stack
Layer1

Orchestrated workflow skills/commands

Multi-step jobs that used to be checklists in my head are now slash commands. Each one chains planning, deployment, QA, and the PR.

  • /plan-and-build: Shortcut story in, deployed metadata out. Reads the story, drafts a plan, builds the field, validation rule, permset, or FlexiPage, deploys to dev, runs QA, opens a PR.
  • /push-through-env: Pushes a feature branch through the Gearset pipeline (dev to qa to staging to main) with safety checks at each stop.
  • /data-upload-leads: Pre-flight automation scan, single-record dry-run, fuzzy-dedup pass, bulk import, verification. The Medicarians round 2 import (86 of 88 records actioned, 47 CampaignMember rows) ran on this skill.
  • /sprint-summary and /sprint-pulse: Auto-generated Shortcut-driven sprint recaps for team-facing readouts as well as user-facing release notes. Mid-sprint health checks for trajectory. Pulse is run on a loop daily at 7am.
  • /sfdc-audit-trail-monitor: Daily Setup Audit Trail scan, classified by severity, posted to Slack. Catches admin-direct prod changes before they cause drift. Allows team to push changes directly in prod if needed (happened once when I was OOO, but i was easily able to catch up and back-propagate all the changes to lower envs).

What used to be 4-5 manual prompts on each multi-step task is now one slash command.

Layer2

Browser automation

For things SOQL cannot confirm: per-record-type field visibility, layout section order, picklist behavior on edit modals, Login As verification across personas. I use agent-browser, a native Rust CLI that exposes accessibility-tree snapshots that Claude drives.

  • /build-sfdc-uat: Generates a ready-to-execute UAT scenarios CSV from a metadata changeset.
  • /sfdc-browser-test: General-purpose UI verification harness.
  • /sfdc-run-qa: Field visibility, layout sections, validation rule QA against the deployed metadata.

Example: the "Closed Reason picklist greyed out on Won stage" bug was a three-layer failure: field dependency, FlexiPage visibility, and classic layout all missing the Won value. Browser automation surfaced it in minutes instead of an hour of clicking around as different users.

Layer3

Remote async via Cursor Cloud Agents

Same engine, different surface. I @-mention Cursor in Slack and it executes work without me opening Salesforce or an IDE.

  • Opens PRs in GitHub against the spark-sfdc repo.
  • Makes SFDC changes directly in sandboxes (and prod when scoped).
  • Updates Shortcut stories with completion comments.
  • Bridges the gap when a request lands in Slack and I am AFK or in a meeting.

Use case: small picklist additions, list view tweaks, field description updates. The kind of work where context-switching into an IDE is more expensive than the work itself.

Layer4

Knowledge graph (lat.md)

The biggest long-term investment in this list, and the one nobody sees day to day. lat.md is a structured, semantically searchable knowledge graph of our Salesforce architecture, business processes, object model, and integrations. It lives in the repo next to the code, gets validated like code (broken links fail CI), and gets queried at the start of every task.

  • OpenAI API key wired into Claude Code's UserPromptSubmit and Stop hooks so the search happens automatically and doesn’t pollute session context.
  • Every new task starts with lat search against the user's intent.
  • Claude grounds itself in actual architecture instead of guessing from file names.

Example: when a new story mentions "Channel Source", lat retrieves the 30-plus PR Channel Source attribution architecture from sc-38847 instantly. Claude does not propose a parallel solution nor does it have to read the codebase directly. It builds on what is already there.

Architectural context loads in one search instead of being re-discovered every task.

Layer5

Project rules and memory

Durable conventions that survive across sessions and even across team members.

  • 12 always-on rule files in .claude/rules/ codify the conventions that fire on most work: how to author a field, scope a permset, the three-layer FlexiPage visibility pattern, data-import quirks of the Bulk API, validation rule exemption patterns. Another 80+ on-demand skills cover deep-reference patterns that only load when their topic comes up.
  • Memory files persist user preferences, project state, completed-work history, and feedback per session. When Claude makes a mistake once and gets corrected, the correction is stored. Permanently.
  • Per-sprint memory indexes shipped work so "like we did for X" resolves without re-reading Shortcut.

Net effect: onboarding the AI to our environment happens once, not every conversation.

Layer6

The /reflection loop

The layers above describe what's there. /reflection is how it stays current.

At the end of any notable session, I run /reflection. The skill scans the conversation for corrections, surprises, domain knowledge I shared, and patterns the agent didn't quite get right. It proposes specific edits: a new rule file, a memory entry, a CLAUDE.md tweak, a fix to a skill.

I review the proposed edits, accept the ones that generalize, drop the ones that don't, and commit them. That's how the system above gets richer each sprint instead of going stale.

Real catches from this loop:

  • Medicarians dedup near-miss. Round 1 of the lead import slipped 3 dupes past the dedup pass because they were the same person under different emails. /reflection captured the gap and codified "fuzzy Name+Company dedup, not just email" into the data-imports rule. Round 2 ran with zero dupe leakage.
  • Silent Bulk API no-ops. During the Account hierarchy backfill, 3 of 4 ParentId updates landed as "success" but didn't actually change anything in prod, because the Bulk API treats blank cells as "leave unchanged" rather than "set to null." /reflection turned this into a rule with the literal #N/A workaround. Caught before the next bulk job ran.
  • Cross-system audit pattern. When I asked Claude to find "Channel Source" the first time, it spent 30 minutes grepping Apex classes that didn't exist. /reflection added a rule to broaden lat.md searches to the business concept first. Saved hours on every subsequent attribution question.

Each loop adds one to a few discrete improvements. The compounding above happens because of this loop, not in spite of it.

Each correction gets captured once and never has to be made again.

Layer7

Manual single-purpose skills

Small but durable. Each one is roughly 50 lines of markdown that codifies the right way to do X in this org.

/commit-and-push, /worktree, /sfdc-retrieve, /pbcopy, /create-gdoc, /upload-to-gsheet, /create-story, /estimate-stories, /organize-temp, and others.

Unglamorous and high-frequency. Five minutes of skill authoring saves a 30-minute task every time it repeats - "do it this way next time" turns into a permanent answer.

Velocity without tech debt

Discipline compiled into the workflow

"Six months in, the next admin cannot move because every change touches three undocumented dependencies. What I've built runs the other way."

Velocity and tech debt usually trade off. In most orgs I've worked in, the engineer who ships fastest is also the one quietly accumulating "we'll fix that later" decisions: picklist values without descriptions, validation rules without exemptions, flows nobody else can read. Six months in, the next admin cannot move because every change touches three undocumented dependencies.

What I've built runs the other way. Every shipped artifact ships with the context that explains it:

  • Description and Shortcut story link on the metadata itself.
  • lat.md entry if the change touches architecture.
  • Rule file entry if it codifies a reusable pattern.
  • Test or QA scenario if it changes behavior.

The 90 tickets shipped this half landed in an org that is more documented, more conventionally named, and more testable than it was on day one. New work gets faster because the discipline is automated. That's why I think of it as a scalability investment, not just a throughput one. The same discipline that prevents tech debt is also what makes each sprint cheaper than the last.

Where this goes next

The next compounding curve

What's next:

  • Context-mode coverage across more workflows. This past week's adoption already pulled “gathering context” from ~17% to ~15%. Expanding to more workflows drives it toward 10%.
  • More routine tickets on cloud-based agents. Cursor Cloud Agents handle picklist additions, list-view tweaks, and field updates from a Slack mention. Pushing them toward bigger autonomous jobs (with review gates) moves that work off my plan entirely.
  • Shared skills across teams. The plugin marketplace I spun up last week lets a skill built once ship to other Spark teams. The build cost is amortized across users, not duplicated per workspace.
